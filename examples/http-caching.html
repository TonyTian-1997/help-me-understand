How HTTP Caching Works

Cache-Control, ETag and 304 are three halves of one deal: keep a copy locally, know how long to trust it, and make double-checking almost free.

1The Pantry and the Sticker — Cache-Control

Explained like you're five

Your browser is a personal assistant who cooks for you; the web server is the grocery store. The trip to the store is slow, so the assistant keeps a pantry — the cache. Every jar from this store arrives with an instruction sticker: "good for 7 days". Within that window the assistant never phones the store at all — pantry wins, dinner is instant.

In real terms, that sticker is the Cache-Control response header. It is the server's complete instruction sheet for how long a response may be reused without asking again. The most common directive is max-age=N — the response is fresh (trustworthy, served from cache with zero network traffic) for N seconds.

The three directives everyone meets first: max-age=604800 (fresh for 7 days), no-cache, and no-store.

Name trapno-cache does not mean "don't cache". It means: store it, but revalidate with the server before every use. "Don't cache" is no-store.
# what the server sends with a long-lived asset
Cache-Control: public, max-age=31536000

# for HTML that should always be re-checked
Cache-Control: no-cache

# for anything personal (banking, API responses)
Cache-Control: no-store
WATCH OUT

private (only the browser's own pantry may keep a copy) vs public (shared pantries — proxy caches, CDNs — may too). Marking personalized responses public with a long max-age is how private data leaks into shared caches.

2The Batch Number — ETag

Explained like you're five

Once the sticker's date passes, the jar is stale — maybe fine, maybe not. Rather than throw it away and buy a new one, the assistant reads the batch number printed on the lid and phones the store: "My jar is batch #a3f9 — is that still your current batch?" One cheap question replaces one expensive delivery.

The batch number is the ETag header — an opaque version tag the server computes for each resource (often a hash of the content). Stale doesn't mean wrong; it means "must check". The ETag is what makes checking cheap. The phone call is a conditional request: the browser re-sends the GET with If-None-Match: "a3f9", meaning "only send me the body if my version is out of date".

There is also a date-based fallback: Last-Modified / If-Modified-Since, used when the server doesn't issue ETags.

Why prefer ETag?File modification times can stay the same while content changes (re-deployed identical timestamp), or change while content doesn't. A content hash is exact.

3"Yep, Still Current" — 304 Not Modified

Explained like you're five

The store's cheapest possible answer is one word — "yep" — and hang up. No jar is shipped; the assistant confidently uses the pantry copy. Only if the batch changed does the store do the expensive thing: deliver a fresh jar with a new batch number on it.

"Yep" is the 304 Not Modified status: the server confirms the cached copy is still valid and sends no body at all — a few hundred bytes of headers instead of megabytes. The browser then "fills in" the content from its own cache and serves it as if it had been downloaded. If the resource did change, the server answers 200 OK with the full new body and a new ETag, and the cycle restarts.

curl -v https://example.com/app.js (second visit)
> If-None-Match: "a3f9i7x2"
< HTTP/2 304
< cache-control: max-age=3600
# no body — the browser reuses its cached copy
WHY IT'S DESIGNED THIS WAY

Cache-Control and ETag/304 solve two different problems: eliminating the request entirely (freshness) versus shrinking the request when it can't be eliminated (validation). A smart deployment uses both: hashed filenames get max-age=31536000 (they never change), while HTML gets no-cache + ETag (always revalidated, but cheaply).
