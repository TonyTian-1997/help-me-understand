How HTTP Caching Works:
the pantry, the sticker, the batch number

Cache-Control, ETag and 304 are three clauses of one deal between browser and server: keep a local copy, know how long to trust it, and make double-checking almost free.

1The pantry and the sticker — Cache-Control

Explained like you're five

Your browser is a personal assistant who fetches your food; every website is a grocery store across town. The trip is slow, so the assistant keeps a pantry — the cache. Smart stores ship every jar with an instruction sticker: "good for 7 days". Within that window the assistant never phones the store at all — pantry wins, dinner is instant.

That sticker is the Cache-Control response header — the server's complete instruction sheet for how long a response may be reused without asking again. The workhorse directive is max-age=N: the response is fresh (trustworthy, served from cache with zero network traffic) for N seconds. Freshness is a promise the server makes once, at delivery time — the browser then enforces it on every later visit, all by itself.

The three directives everyone meets first, and the trap in their names [S1]:

# a file whose content never changes (its name has a hash in it)
Cache-Control: public, max-age=31536000

# HTML that must always be re-checked before use
Cache-Control: no-cache

# anything personal — banking pages, logged-in API responses
Cache-Control: no-store
Name trapno-cache does not mean "don't cache". It means: store it, but revalidate with the server before every use. "Don't cache" is no-store.
RISK · the leak everyone ships once

private means only the browser's own pantry may keep a copy; public invites shared pantries — proxy caches, CDNs — to store one too. Marking a personalized response public with a long max-age is how one user's data ends up served to the next user behind the same corporate proxy. When in doubt: private.

2The batch number — ETag

Explained like you're five

Once the sticker's date passes, the jar is stale — maybe fine, maybe not. Throwing it away and buying a new one is wasteful. So the assistant reads the batch number printed on the lid and phones the store: "My jar is batch #a3f9 — still your current batch?" One cheap phone call replaces one expensive delivery.

The batch number is the ETag header — an opaque version tag the server computes for each response, typically a hash of the content [S2]. Stale doesn't mean wrong; it means "must check". The ETag is what makes checking cheap. The phone call is a conditional request: the browser re-sends the GET with If-None-Match: "a3f9" — "only send me the body if my version is out of date".

There is an older, date-based fallback: Last-Modified / If-Modified-Since, used when a server doesn't issue ETags. Both mechanisms are called validators — the things a revalidation request carries to prove which version the browser already has.

Why prefer ETag?A file's modification time can stay the same while its content changes (restored from backup), or change while content doesn't (re-deployed identical bytes). A content hash is exact.

Deep dive ① — strong vs weak validators

Explained like you're five

A strong batch number promises: same number ⇒ same jar, byte for byte. A weak batch number (marked with a W/ prefix) only promises: same number ⇒ same dish, even if plated differently — the layout may differ, the meaning doesn't.

ETag: "a3f9i7x2"      # strong: byte-identical guarantee — safe for ranged requests
ETag: W/"a3f9i7x2"   # weak: semantically equivalent (common behind CDNs that
                        # re-minify or re-compress on the fly)
When weak is requiredA CDN that re-compresses images per device can't promise byte equality, so it issues W/ tags. Fine for whole-file caching; not fine for resuming a partial download.

3"Yep, still current" — 304 Not Modified

Explained like you're five

The store's cheapest possible answer is one word — "yep" — and hang up. No jar is shipped; the assistant confidently serves the pantry copy. Only if the batch changed does the store do the expensive thing: deliver a fresh jar with a new batch number.

"Yep" is the 304 Not Modified status: the server confirms the cached copy is still valid and sends no body at all — a few hundred bytes of headers instead of megabytes [S3]. The browser then "fills in" the content from its own cache and serves it to the page as if it had been downloaded. If the resource did change, the server answers a plain 200 OK with the full new body plus a new ETag, and the cycle restarts.

# curl -v https://example.com/app.js — the second visit
browser has app.js in cache, sticker expired yesterday
├ GET /app.js + conditional headers → proves which version it holds
│  ├ If-None-Match: "a3f9i7x2" → the batch number
│  └ If-Modified-Since: Mon, 01 Sep 2026 … → date fallback
├ server recomputes the file's hash → matches "a3f9i7x2"
└ < HTTP/2 304 — zero body bytes
browser merges 304 headers onto cached body → page gets a normal response it never had to download

4The full journey — who talks to whom

Explained like you're five

Zoom out: the assistant (browser) serves you from the pantry; a shared pantry on the road (CDN) may hold copies for a whole neighborhood; the store (origin server) is where truth lives. Every arrow in between speaks the same sticker-and-batch-number language.

The practical consequence: Cache-Control and ETag/304 solve two different problems [S4] — eliminating the request entirely (freshness) versus shrinking the request when it can't be eliminated (validation). A smart deployment uses both at once:

AssetStrategyWhy
app.8f3c21.jspublic, max-age=31536000hashed filename ⇒ a new deploy is literally a new URL; the old copy is valid forever
index.htmlno-cache + ETagmust always reference the newest hashes, but the 304 check costs ~nothing
/api/meprivate, no-storeper-user, never shared, never even locally persisted

5Gotchas that bite in production

Explained like you're five

Stickers are cheap to print, so assistants follow them literally. If you sticker the daily newspaper with "good for a year", don't be surprised when visitors read last year's news.

SymptomUsual causeFix
Deploys don't show up for some usersindex.html cached with long max-ageHTML is no-cache; only hashed assets get years
User A sees user B's dataAPI response marked public, cached by a shared proxyprivate or no-store on anything per-user
Page looks broken after deployold HTML references hashed files that no longer existkeep old assets deployed for a grace window, or both errors vanish together
Cache "ignores" ETagresponse also had Vary: Cookie that changedVary keys the cache entry — treat it as part of the sticker
PHIL · why the server refuses to guess

Nothing in the pipeline "checks sometimes" — freshness is deterministic (max-age elapsed or not) and validation is provable (validators match or don't). That determinism is why a CDN can serve millions of requests without ever phoning the origin: every hop answers the same two questions the same way.
